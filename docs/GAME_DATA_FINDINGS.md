# Game data findings (strings, INI files, dialogue, item/creature templates)

## English.stf -- the string table (`src/assets/stf.{h,cpp}`)
12-byte header `u32 version=3, u32 1, u32 count (3281)`, then `count` 16-byte records `{u32 offset, u32 length, u32 file_size, u32 0}`; the text follows contiguously (plain bytes, no NUL).
**String ids are 1-based** (0 = none): the generic-entity chunk `GENT` of every template starts with `u32 name_id, u32 description_id` (e.g. `.44 Revolver` GENT 1930 -> text #1930 = ".44 Revolver"; Cpl. Armstrong's critter
file: 427 "GMC Soldier", 428 "You see soldier of the Great Midwest Com..."), scripts use the same ids (`RegisterNodeText(850)`, `DisplayStringRef`). Markup seen in NPC speech: a `{c16711680}` colour prefix (decimal 0xFF0000).
`Engine/tokens.txt` maps name tokens to string ids (`DEVILDOG=1986` ...) for `{token}` substitution (`SetTokenStrref`).

## Engine/sys.ini (the engine's own settings; read it instead of guessing)
* `[Camera]`: `Distance Min = Max = 350` (fixed), `FOV Min 6 / Max 15` degrees (**zoom is the field of view**: a near-orthographic telephoto look), `Elevation Min 38.5 / Max 89`, `Azimuth Speed 360` deg/s,
  `Scroll Speed 96` units/s, `Scroll Border 0.01`, `FOV Speed 6.5`, `Elevation Speed 360`, `Distance Speed 800`. `vanburen` uses these (tilt fixed at 38.5, default FOV 8 fitted to the new-game screenshot).
* `[Server] Start map = 00_03_Tutorial_Junktown.map`, `Start map entry point = 0`  (=> the new-game start is Junktown, as found from the screenshot).
* `[World]` start clock 2253-10-18 13:13:13, `Seconds Per Round = 6`.  `[Mainmenu]` map `mainmenu.map` with its own camera (fov 68); `[CharGen]` character positions/yaw on the chargen map; `[Audio]` GroupList `FO3.gls`, MusicJumpList `F3.sco`.
* `Engine/model.ini`: per-socket model/texture variation naming for characters (socket ids follow the G3D file format); `Engine/DefaultInterface.ini` + `Interface/*.ini|.gui` UI definitions (not decoded; `.gui` = "GUI V1.3" binary).

## Dialogue (`Scripts/*.sma`, 36 files)
The `.sma` files are **AMX programs too** (same format as `.scr`, see AMX_FORMAT_FINDINGS.md), one per speaking NPC/terminal (`00 Corporal Armstrong.sma`, `04 Marie.sma`, `07 Azkee.sma`, ...). Their publics are the dialogue graph:
`OnStartDialogue` (sets the first node), node functions `N<n>`/`NU<k>_N<n>` (node text), reply functions `R<A|C|L><k>_N<n>` and link functions `L<A|C><k>_R<r>_N<n>` -- `A` = action (run when chosen),
`C` = condition (returns whether the reply is shown), `L` = link target. Natives used only by dialogue scripts: `SetCurrentNodeName(name)`, `SetNodeTextFunction(func)`, `RegisterNodeText(strid)`,
`RegisterReply(...)`, `RegisterLinkToOtherDialogue`, `DialogueCall`, `PCSpeaker`, `WasLastNodeName`, `IsInDialogue`, `StartStore`, `GiveNewItem`, `PartyHasItem`, `IsInParty`, `HasDied`, `OpenTask/CloseTask`.
Running `00 Corporal Armstrong.sma::OnStartDialogue` in the VM with logging natives gives: `GetGlobal("00_Vault_Door_Seen")`, `SetCurrentNodeName("Node 2")`, `SetNodeTextFunction("NU2_N2")`,
`RegisterNodeText(850)` (text #850). Engine strings: `DialogueManager::BeginDialogue() - Error loading script`, `Jump Link Failed: Unable to load dialogue script %s`, `GameActionInitiateDialogue`, GUI `Dialog.gui`.

## Script attachment
`EEOV` (per-placed-entity override, in maps) holds the script file name `*.amx` (e.g. `00_TutorialDefault_VaultDoor.amx`); the shipped bytecode is `Scripts/<name>.scr` (the `.amx` extension is the source-side name).
The map's `vars` list in the same chunk are script globals preloaded by name (engine warning: "Variable %s not found while preloading script %s"). Map triggers (`ESTR`) name `.amx` scripts too.

## Item / weapon templates (partial)
* Template layout (all kinds): `EEN2` (model name, icons, EEOV), `GENT` (name_id, desc_id, ...), then a kind chunk: `GITM` (inventory item), `GIWP` (weapon), `GIAR` (armor), `GCRE` (critter), `GOBJ`/`GDOR` (door), ...
* `GIWP` = fixed part (62 bytes in the .44 revolver) + one `GWAM` v5 chunk per attack mode. Verified by correlating with the Van Buren wiki infoboxes in `reference/van_buren/items_and_equipment` over ~49 weapons:
  GWAM word 6 = **range** (10/10 matches), word 12 = **AP cost as 16.16 fixed point** (9/11 matches; .44 revolver Single 15 AP -> 983040, Butt smash 9 AP -> 589824), in the melee mode words 9/10 = damage min/max (4, 10).
  Ranged damage and ammo capacity are not in the same words (probably in the ammo template / the fixed part, whose length varies) -- not yet decoded.
* Critters: `GCRE` lists portrait + worn parts (see MAP_FORMAT_FINDINGS.md); numeric stats not decoded yet.

## Engine native table (F3.exe strings; names registered with the VM)
The names the engine registers (144 identifiers around `StartStore`, e.g. `SetPosition GetPosition TeleportParty JoinParty LeaveParty SpawnEntity DestroyEntity DropItem GiveNewItem TransferItem* QueueFunction StartCutscene
GetValue SetValue IncValue DecValue GetGlobal/IncGlobal/DecGlobal RandomNumber(Float) SecondsPassed..YearsPassed SetHeightFog SetCameraFog SetWorldMapArea* SetEncyclopediaData ...`) are a superset of the 124 natives
the shipped scripts call (109 in `.scr` + extras only in `.sma`).


## Critter template stats (GCRE / GENT) -- verified over all 100+ `.critter` files
GCRE payload, u32 words: `[0..6]` = **SPECIAL** (ST PE EN CH IN AG LK; Armstrong 7 7 7 5 6 6 5, Default_PC 6 x7, dogs 5, props 0), `[10]` = race (5 = robot/eyebot and the destructible props, 3 = animals; scripts test `GetRace()==5`),
`[11]` = age, `[12]` = gender (0 male, 1 female; scripts: `GetGender()==0` -> the `HM...` male voice set), `[13]` = **team** (1 = the player's friends: Armstrong, vault dwellers; 2 = the hostile insurgents; 3 Frank/Bobby/Shelley; 4/6 Blackfoot villagers; 0 = none, the script creates one).
GENT words: `[0]` name string id, `[1]` description id, `[6]`/`[7]` = hit points / max hit points (Armstrong 80, insurgents 20-35, dogs 15, Default_PC 100). The map script of Junktown sets "team 2 enemy of team 1" -- that is how the tutorial's insurgents become hostile.

## Script runtime (`src/game/world.{h,cpp}`) -- how the shipped scripts talk to the engine
The scripts keep their debug symbols (`SYMBOL` records in the code stream: variable and function names, parameter names; `amx_parse.py` + `scratchpad/syms.py`-style dumps), which gives the exact protocol:
* **Entry points** (args in call order): `OnCreate(time)`, `OnLoad(time)`, `OnUpdate(time)`, `OnDeath(time)`, `OnDestroy(time)`, `OnDamage(time, source, amount, type)`, `OnAttacked(attacker, target, hit, location, volume)`, `OnMessage(sender, id)`,
  `OnOpen(entity)` / `OnClose(entity)` (doors/containers; **return 1 = allowed, 0 = refuse** -- the vault-door script returns 0 while `IsLocked`), `OnEnter(entity, time)` / `OnLeave(entity, time)` (script trigger zones), `GetUsableSkills(params[])` (fills `[id, strref]` pairs: 1 = Repair on robots, 2 = Heal), `UseSkill(entity, id)`.
  `time` = game milliseconds. **Angles are integer degrees, distances integer world units** (the scripts carry a 1-degree sine table), positions are float triples written through an array argument.
* **Public variables** `p_<name>` (AMX pubvars table) are set from the map entity's EEOV `vars` list before `OnCreate`.
* The map itself has a script named like the `.map` file (`00_03_Tutorial_Junktown.scr`): it hides the two ambush insurgents (`FindEntity` by instance name + `DeactivateEntity`) and sets the team attitudes. Script zones are `ETTR/ESTR` map triggers of type 1 (target = the `.amx` stem), type 0 = map transition (target map, entry point id), type 6 = boundary polygons (building outlines, not used by scripts).
* **AI**: each critter script is a hierarchical state machine (`StateDefault/Combat/Search/Flee/Dead/Talk`, `CanDetect`, `UpdateEntityLists`, ...) driven by `OnUpdate` and by the engine's `OnMessage(sender, 1)` (a perception message the engine sends when someone is near), using `FindObjects(&list, pos[3], radius)` -> count (list handle stored through the first argument) + `GetObject(list, i)`.
  Attitudes: 0 neutral, 1 ally, 2 wary, 3 enemy (case order of the OnMessage switch); own team = ally.
* **Natives** (arg order = Pawn order): `Myself() Protagonist() PCSpeaker()`; `GetPosition(e, pos[])` `Distance(a,b)` `PointDistance(pos,pos)` `GetFacing(e)` `SetFacing(e,deg)` `SetFacingTarget(e,t)` `GetDirectionToEntity(a,b)` `GetLOS(a,b)`;
  `GetTeam/GetSquadID/GetTeamRank/GetSquadRank`, `CreateTeam() CreateSquad() AddToTeam(e,t) AddToSquad(e,s)`, `Get/SetTeamAttitude(a,b[,att])`, `Get/SetSquadAttitude`;
  actions are queued per entity and run one after another: `A_Wait(e, ms)`, `A_MoveToPosition(e, pos[], run, ?)`, `A_MoveToEntity(e, target, run, ?)`, `A_Wander(e, ulPos[], lrPos[], ?)`, `A_PlayAnim(e, id, ...)` (on a door: open it), `A_Attack(e, target)`, `A_FloatingSpeechText(e, strref, duration_ms, r, g, b)` (blocks for the duration),
  `ClearActions(e)`, `IsIdle(e)`; **actions work on the protagonist too** (the vault-door console queues `A_Wait(player, 9500)` + `A_MoveToPosition(player, ...)`: the script walks the player into the vault);
  `FloatingSpeechText(e, strref, duration_ms, r, g, b)`, `FloatingDamageText(e, text, r, g, b)`, `DisplayStringRef(strref, r, g, b)`; `SendMessage(target, id, &arg...)` (extra arguments are **by reference**; `MessageArgCount()/MessageGetArg(i)` inside `OnMessage`);
  `GetGlobal(name) SetGlobal(name, v)` (defaults in `Scripts/globals.ini`), `SetValue/GetValue(e, key, v)`, `RandomNumber(min,max)` inclusive, `GetTimeStamp() SecondsPassed(stamp) Hour() Minute()`;
  `FindEntity("instance name")`, `MatchEntity(&list, "pattern*")`, `GetWayPointCount("Waypoint01") GetWayPointPosition(name, i, pos[])` (map `EPTH` paths), `OpenTask(id, ?) AddEntry(task, strref) CloseTask(task, state)` (journal: the task id doubles as the title's string id), Pawn `float*` natives.
* **Dialogue** (`Scripts/<entity display name>.sma`, e.g. display name `00 Corporal Armstrong`): `OnStartDialogue()` calls the first link function, which runs actions and calls a node function `N<k>`; the node function calls `SetCurrentNodeName`, `SetNodeTextFunction("NU..")` and `RegisterNodeText(strref)` (what the NPC says);
  the engine then runs the node text function, which calls `RegisterReply(index, strref, "RA..", "RL..")` for every reply whose condition `RC..` holds. Choosing a reply runs its action function (`RA`) then its link function (`RL`); if the link enters no new node the conversation ends. An empty reply string (id 849) means "continue". Some `.sma` are barks only (`FloatingSpeechText`, no node text).
  Text markup: `{c255}` colour prefix (dropped), `<CHARNAME>` = the player's name, `<TOKEN>` = `Engine/tokens.txt`, language-filter words.
* Not yet: trading (`StartStore` is a stub), sound (`AttachSound` returns ids only), visual effects (`AttachVEG`), map effects, the party.

* **Items and inventory** (`World::bag`, `equipped[4]`, `Entity::cargo`): item templates give name / description (GENT words 0 / 1 -> string ids), kind (weapon armor ammo use item) and icons (`EEN2` strings: `[0]` inventory icon `*_INV`, `[1]` action-bar icon `*_ACT`; the 64x64 / 128x64 TGAs live in `Interface/`).
  Equipment slots 0 head, 1 body, 2 / 3 hands. Armor goes to the head slot when its parts (GITM strings, e.g. `HeaMotorcycle`) have a `Hea*` part and no `Bod*` part. Stackable: ammo, consumables, misc. Containers and corpses carry the map entity's item list (`.veg` entries skipped); opening one sets `World::openContainer` and the host shows the Container window.
  The natives `HasItem / PartyHasItem / IsItemEquipped / EquipItem / GiveNewItem` take the item as a string (matched case-insensitively against the template file name or display name); **their exact signatures are unverified** because none of the shipped scripts reaches them in the headless runs (no script in `Scripts/` names an item file). A call whose item argument is not a string is noted in `World::debug`.
  Not decoded: weapon / ammo stats (`GIWP`, `GIAM` words: damage, range, ammo capacity), item weight and value (`GITM`), so the window shows names and descriptions only.
* **Combat** (`World::tryAttack`, `startCombat`, `combatAi`, `weaponStats`): **turn based** (the tech demo's options list "Combat Mode: Turn Based / Real Time / Ask Me", strings 542-551; only turn based is implemented). Most of the rules below are my own placeholders: nothing could be tested against the tech demo.
  *Flow:* combat starts with the first attack (the protagonist's, or an enemy script's `A_Attack` against someone within 45 units); the protagonist's side (team 1) and every enemy (team attitude 3) within 40 units take part and act in sequence order (2 x perception, random tie break, the attacker first); a turn gives 5 + agility / 2 action points. An attack costs the weapon's AP (guns 4, melee / fists 3; the bar shows "4AP"), moving costs 1 AP per 2 world units, reloading and using an item 2. Combat ends when no enemy is left alive. Enemies and allies are played by the engine (`combatAi`: target = what the AI script last asked to attack, else the nearest enemy; run into range, attack while it can pay, pass); their scripts' own move / wander actions are dropped while they fight, and the scripts still run for speech and state. The protagonist's turn ends when the action points are gone, on Enter, or with the End Turn button (`btnSneak` repurposed: Sneak does nothing in the tech demo; its caption is drawn by the host as "End Turn", grayed out outside combat). When the protagonist dies the world freezes (the shipped AI scripts spin forever without a living protagonist) and Enter restarts the map.
  *Interface:* clicking an enemy only walks up to them. The two weapon buttons on the action bar are the combat actions: click one (it is drawn pressed, the cursor becomes the attack crosshair), then click a target; the player walks into range if needed (paying AP) and strikes. The button's caption is the mode (strings 330 SINGLE, 350 MELEE, 332 UNARMED) with its cost ("AP4"); a gun whose clip is empty shows RELOAD (389) and the click reloads. The bar's pips (`picAPIcon`, `f3_actionbar_APfine_green` / `_grey`) show the action points left. On death the 3D scene fades to gray and a slight blur over 3 seconds (the interface and the YOU ARE DEAD banner stay as they are).
  *Decoded from the templates (heuristic):* `GIWP` word 0 = class (6 = melee), word 2 = clip size; the first `GWAM` (attack mode) block inside it: word 0 = mode (2 single, 1 burst, 6 / 8 melee), word 6 = damage (50 for the machine pistol, 20 for the 9mm pistol, 5 for the knife), word 12 = a 16.16 number (15 / 18 / 20 for guns, 8-12 for melee, so not a melee range). `GIAR` word 0 = normal-damage resistance (leather 4, motorcycle helmet 16, power armor 32).
  *Damage model (placeholders):* ranged damage = 0.4 x the raw damage word, range = the range word (min 15 if unset), melee reach 2.6, fists 3 + (strength - 5) over 2.2; +/-20 % roll, melee adds strength over 5; hit chance 80 + 3 x (attacker agility - 5) - 2 x (target agility - 5) - 1.5 x distance (melee 85, no distance term), clamped 10-95; armor = percentage reduction (body + helmet resistance words, max 80 %). Unfinished weapon templates (62-byte `GIWP` stubs: baseball bat, crowbar, grenades, ...) use defaults and are treated as melee by name. A critter fights with the first weapon in its inventory (fists / natural attacks if none); the protagonist with the weapon in the selected hand. The protagonist's guns have clips; reloading takes one ammo item whose name contains the weapon's caliber token ("9mm", ".45"), or an energy cell / fuel for weapons without one. Enemies never run out.
  *Held weapon models:* an item template's model (`GD_WP_x`) is the ground-drop shape; the weapon in a hand is a separate model `WP_x.g3d` (`Items/`), skinned to its own skeleton `WP_x.skel`: `Weapon_1` (main grip: attach it to the character's `R Handle_1` bone with an identity offset), `Weapon_2` (the off-hand grip of two-handed weapons; the left hand follows from the two-handed animations), `FX_Muzzle` (muzzle flash position), `FX_Brass` (ejected shell position). The mesh also holds small FX shapes weighted to the FX_* bones, which must not be drawn. The firing animations `WP_x_Single.anim` / `_Burst.anim` (recoil, barrel spin; the minigun only has `_Burst`) are played on the weapon skeleton while the shooter's attack animation runs, and `FX_Muzzle` / `FX_Brass` give the world positions for the effects. The two-handed animation set is `HumM_Com_2HH_*` / `Def_2HH_Idle`.
  Animations (`Level::EntDraw`): `_com_1h_gun_shoot_01`, `_com_1h_melee_slash_01`, `_com_una_punch_jab_01` / `_attack1_01` for animals, `_com_una_dmgfr_01` for being hit, `_proneb_una_death_01` for dying. *Effects* (`tools/common/fx.h`, hand-made stand-ins; the `.vfx` effect files themselves are decoded in `VFX_FORMAT_FINDINGS.md` but not used yet): per attack, 0.2 s into the animation, a muzzle flash (star + glow, orange / red for energy and flame weapons), a tracer, an ejected brass shell, and sparks at the target on a hit (a dust puff where a miss lands); blows only throw sparks on a hit. `World::Entity::shotSerial / shotTarget / shotHit` tell the host which attack to show. Not done: sound, called shots, burst mode, sneaking, thrown weapons / grenades, area damage (exploding barrels), critical hits, experience, the tech demo's real sequence / AP / evasion formulas, "ask me" and real-time modes.

## GUI layouts (`Interface/*.gui`, "GUI V1.0..V1.3") -- `src/assets/gui.{h,cpp}`, `gui_parse.py`, `build/vb_gui_dump`
Decoded from F3.exe (loader `0x495b50`, `Window::Load 0x4b10f0`, button `0x4a6b60`, label `0x4aa640`, picture `0x4ab190`, skin fragment `0x4b20a0`). All little-endian, strings are `u32 length + bytes` (no NUL), rectangles are `x0,y0,x1,y1` as i32.
```
"GUI " "V1.x"  (x = 0..3 -> version 1..4)   string name ("Actionbar.INT")   u8 0   u32 topWindowCount   topWindowCount x { u32 type, Window }
Window(version v, type t):
  [t == 1 button: u32 buttonId, (v>=4) u8 checked, 3 x string (sound file names)]
  rect (design rect), string name, u8 a, u8 b, u8 c, string skin.ini, u32 colour (ARGB tint), rect (working rect, same values),
  (v>=2) u8, u32;   (v>=3) string, i32, string, i32, string   (sound slots, usually empty / -1)
  9 x skin fragment { u32 flags(0 fixed,1 stretch x,2 stretch y,3 both) w h u3 u4 u5(=1), string texture, f32, u32 colour, rect }   (corners/edges/middle of the window skin; a *picture's* image is the middle fragment)
  { u32 id ; string }* terminated by id 0xffffffff        (per-window string table, unused by the shipped layouts we render)
  u32 childCount, childCount x { u32 type, Window }
  [t == 3/4 label: u32 textId (STRING TABLE id of the caption, e.g. 262 = HEALTH), string font face ("Arial" / "Fallouty"), 4 x u32 (.., size, .., ARGB colour), u8, u8, u32 alignment (0 left, 1 right, 2 centre), 4 x u32, u32]
types: 0 window, 1 button, 2 picture, 3 label, 4 label subclass (its extra fields not decoded: AreaMap.gui and DebugTools.gui do not parse yet; the other 23 files consume exactly every byte)
```
Child rectangles are relative to the parent; the root window of `Actionbar.gui` is a dummy 96x96, its child `picBackground` is the 1024x164 bar (texture `f3_actionbar.tga` 800x128, drawn stretched x1.28), laid out for a 1024x768 screen.
Actionbar contents: `btnWeapon01/02` (weapon slots, each with `btnUp`/`btnDown` pictures holding icon, mode label, AP label), `picPlayer00..05` (party strip: name label + yellow health / blue fatigue bar images),
`winHealth/Fatigue/EvasionDigit1/10/100` (rolling counters: `f3_digit_0..9.tga`, RLE true-colour TGAs -- `tga.cpp` now handles type 10), `lblActionPoints` + `lblActionPointsValue`, and six 36x36 red buttons `btnSneak btnInventory btnPipBoy btnUseSkill btnCharacter btnOptions` with caption labels.
`Inventory.gui` (1024x604, sits directly above the bar): backpack 3x6 cells of 60 units at (68,96), equipment frames at x 316 (y 72 / 212 / 348 / 488), description box (460,400); `Container.gui` (256x176): 10 slots (5x2), Take All, Done. Drawn by `tools/common/invwindow.h`.
`vanburen` draws the bar (`tools/common/actionbar.h`, `uidraw.h`): scale = window height / 768, centred at the bottom; fonts via FreeType from the game's `Fonts/` (`r_fallouty.ttf` = "Fallouty"; "Arial" is not shipped, the condensed Gothic `TT0807M_.TTF` stands in).

## Tech demo executable: skipping character creation (2026-10-24)
In `F3.exe` the main menu's button handler (Ghidra `FUN_00440ce0`) treats `NewGameBtn` in two ways: with **Shift held** (`GetAsyncKeyState(VK_SHIFT)`, call at VA `0x440d6d`) it runs the console command `RequestNewGame` (the debug "New Game (dbg)": default player `Default_PC.CRT` with its debug kit, straight into the start map, Junktown), provided the single / multiplayer toggle is off; without Shift it opens the character creation windows (`CharGen_NAS.INT`, `winStats`, `winModel`, ... via `FUN_0042f9e0`). `tools/patch_f3_newgame.py apply` replaces the `JNS +0x64` at VA `0x440d75` (file offset `0x40d75`, bytes `79 64`) with two NOPs, so Start New Game always takes the Shift branch. Reversible: `tools/patch_f3_newgame.py revert` (the script refuses to touch anything that is neither the original nor the patched bytes; the original stays as `F3.exe.orig`; original SHA-256 `4652a3d0...b87`). Tested under Proton with `run_f3_windowed.sh`: Start New Game goes to Junktown ("Welcome to Fallout.") with no character creation. Without the patch, holding Shift while clicking the button does the same. Console commands registered next to it (`FUN_0058e900`): `StartMap <map>`, `RequestNewGame`, `NewGame`, `Connect`, `CreateEntity`, `SetScript`, `GetGlobal` / `SetGlobal`, many `Toggle*` and `Camera*` commands; `+Ctrl+N` is bound to `RequestNewGame` in `F3.ini`.

Startup splash videos: `F3.ini` `[Graphics] enable startup movies = 0` (the game also has a `ToggleStartupMovies` console command) starts straight at the main menu; no exe patch needed. Set 2026-10-24 in the Proton prefix's `Documents/F3/F3.ini` (backup `F3.ini.bak`; set it back to 1 to restore them).

## Movement speed (2026-10-24)
The walk / run animations (`HumM_Com_Una_Walk_01` 1.0 s, `..._Run_01` 0.5 s) play in place (the root bone does not move), so the ground speed is not in the assets. The first guess (5.4 / 10 units per second, from the footfall rate) looked half as fast as the tech demo, so `World::kWalkSpeed` = 9 and `kRunSpeed` = 16 now (first tried 10.8 / 20, "about twice", which the user found a tad too fast). For reference, the planted foot slides back relative to the body at about 7.7 units/s (walk) and 17 (run) in the animation, i.e. the no-foot-slide speeds would be a little lower; `VB_DEBUG_STRIDE=1` prints the foot tracks. Still to verify against the demo if possible.

## Hover highlight (2026-10-24)
The hover effect is defined in the assets: `Effects/FX_Selection_Critter_Medium_01.vfx` (looping) with a `highlight` MODELEFFECT (recolours the hovered model with `Color 46fffb` -> `FinalColor 00c1bc` on a sine, unlit) and two MODEL effects `select1` / `select2` = `Disc_select_01.g3d` (texture `select_01.tga`, the crosshair circle, `ScaleX/Z` 0.3, additive, alpha 255 -> 100 on a 1 Hz sine) and `Disc_select_02.g3d` (`select_02.tga`, two arcs, scale 0.34), both lying on the ground (offset 0.01). The discs' g3d materials carry the spin: the material trailer's bit 4 holds three doubles = texture rotation (centre u 0.5, centre v 0.5, speed): **-0.05** for the crosshair disc and **+0.2** for the arcs, i.e. opposite directions (bit 3 of disc 1, `1.0, 0.0`, is still unknown). The unit of the speed is a guess (revolutions per second). `vanburen` reads all of this from the files: the disc scale is applied to the 12.73-unit mesh (so about 3.8 units across for a critter; doors x1.8, containers x1.3, items x0.7 are guesses, only the Critter Medium file exists), the texture rotation is a `uvRot` uniform in the model shader, and the highlight is the model redrawn with its texture reduced to light / dark (`lumaOnly`) times the pulsing colour. The name label next to the cursor (`World::nameOf`, "(dead)" for bodies) is the port's own addition from the screenshots; it is shown for everything except doors (the user did not want popups over doors, 2026-10-25). Hover is ignored while a window, the bar or a dialogue is under the mouse; nothing outside the light circle (fog radius r1 - 0.5) can be picked: no glow, no use cursor, no click, doors and containers in the dim fog included (user, 2026-10-25, confirmed in the demo).

Fog and combat effects (2026-10-24): footprints, dust puffs and other non-map effects fade with the same soft edge as the lit disc (`VfxRuntime::fogAlpha`, 1 inside `fog.r0`, 0 at `fog.r1`; per particle, sprite and decal corner). Before, a print that fell in the dimmed band between r0 and r1 was drawn at full brightness, a bright glitch in the shadow. Map emitters (fires, steam) ignore it and stay visible everywhere.

Starting the tech demo in another map (2026-10-24): open the in-game console with the backtick key (`+\`` = `ConsoleWindow` in `F3.ini`) and run `RequestNewGame <map>`, e.g. `RequestNewGame 00_04_Tutorial_Vault` (the handler `FUN_0058dbe0` takes one optional argument, the start map, then starts a new game with the default player; verified: the log shows `Map::Create( 00_04_Tutorial_Vault.map )`). ## The player's light is a field of visibility (2026-10-25, from the user's demo screenshots)
In the demo the circle of light is not a flat disc: it behaves like a sphere of light that radiates from the player and responds to the surroundings (corridor walls light up, the rooms behind walls stay dark, a pool of light appears in a side room seen through a doorway, cliffs and buildings cut the light). The port now does this (`tools/common/lightfield.h`, `gmodel.h` `fogLight`): (1) a **field of visibility** on the collision grid (0.5 unit cells): a cell is lit when a straight line from the player's cell reaches it without crossing a blocked cell (collision value 47 = walls, buildings, cliffs and the void outside the map, plus closed doors, which `vanburen` blocks in the same grid; **not** value 44 = prop footprints: in the demo traffic lights, barrels and the like cast no shadow of light, `NavGrid::blocksLight`); the first blocked cell on a line is lit itself, so the wall faces towards the player light up; the mask gets two 3 x 3 blur passes for a soft edge and is recomputed when the player changes cell or a door opens / closes (about 3 ms, `VB_DEBUG_LIGHT=1`); (2) a **spherical fall-off**: the shaders multiply the mask with `1 - smoothstep(r0, r1, d)` where `d` is the 3D distance from a light point 4 units above the player's feet (r0 20.5, r1 26), so higher parts of walls are dimmer than their base; (3) everything that used the old disc now asks `litAt(x, z, y)` (the same formula on the CPU): who is drawn, who can be hovered / clicked / talked to, speech in the fog, `IsUnderFOW`, effect visibility and fade, and the explored memory of fog style 2. Not done / guesses: terrain height is not an occluder (hills and cliffs only cut the light where the collision grid marks them), props (value 44) do not block light as the user saw in the demo, how the demo decides this (the props are part of the map there) is unknown, the light point's height and the blur are guesses, `OnAutoClose`-style door timing, no map light sources (lamps, console lights) yet.

Light blockers, second pass (2026-10-27, user: the traffic light and a bush under a billboard still cast light shadows). Two causes in the port, both fixed: (1) the port also marked the footprints of props / containers (which `vanburen` blocks in the nav grid for walking, `propBlock`) as light blockers; now only (a) big 8-connected blobs of collision value 47 (`NavGrid::wallish`, at least 20 cells = 5 square units: buildings, cliffs, walls; poles and other small blobs are ignored) and (b) the cells of closed doors (`NavGrid::doorOcc`) block light. What the demo really does is not known; the evidence from the engine (Ghidra, `F3.exe`): the renderer has **stencil shadow volumes** (`Gfx_RenderManager::RenderShadowVolumes2` at 0x4915e0, the options menu entry `picShadowType` = None / Projected / Stencil Volume, console command `ToggleShadow`, effect properties `CastShadow` / `UseShadowVolume`), so the player's light is a real light whose shadows come from shadow volumes, and every mesh group has a cast-shadow flag: the material parser at 0x4d5900 recognises the name tokens `TWO_SIDED` (+0x90), `FLAT` (+0x91), `FLOOR` (+0x92), `NO_SHADOW` (+0x93), `BTM_STORY` (+0x94), `BTM_STORY_INT` (+0x95), `TOP_STORY` (+0x96) and `BLD_NUMnn` (+0x98) and the group converter at 0x5277c1 stores `!TWO_SIDED` at +0x68 and `!NO_SHADOW` at +0x69 (= casts shadow). Which bit means "no shadow" is not decoded. If the size heuristic is not good enough, the exact rule can be found by decompiling the shadow-volume builder (callers of 0x4ac190) and the octree users of `leaf + 0x54` (the FLGS array, read at 0x5af800). `VB_DEBUG_CELLS=x,z` prints an ASCII map of the blocking cells around a point (W = wall blob, D = door cell, + = blocked prop, o = small blob).

(2) `*.sndconf` = the text source of a "preset" (the engine compiles it to the `.psf` names that maps and effect files use; no `.psf` ships): header `PlaySequencing n`, `FullSoundRadius`, `NoSoundRadius` (world units: full volume inside, silent beyond, linear between), then per sample `file.wav { BaseVolume, RandomVolume (percent, +-), BasePitch, RandomPitch (percent), BaseOffset, RandomOffset (ms) }`. A `.psf` name with no `.sndconf` (wind, vents, fires, generator, glass, eye bot) is just `Sounds/<stem>.wav` with the group defaults 40 / 60. Inferred: `PlaySequencing` 2 = pick at random (the footstep presets with four variants), 1 = in order (single sample), 0 = in order (only a test file); `BaseOffset` / `RandomOffset` = the gap in ms before a looping preset plays its next sample (the coyote howl: 6 s sample, offset 300 + up to 10000 ms; the computer bleeps: up to 100 ms), not a start offset.
